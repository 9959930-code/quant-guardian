## 주요 설계 판단과 이유

### 1. 예산은 전략 입력이 아니라 개인 표시 입력이다

전략이 40%를 제안할 때 500만원 사용자는 200만원, 1,000만원 사용자는 400만원을 목표로 계산하면 된다. 예산이 바뀔 때 신호까지 바뀌면 동일 전략을 사용자별로 비교할 수 없으므로 시장 엔진과 개인금액 계산을 분리했다.

### 2. 자동 텔레그램과 사이트 예산은 기본적으로 동기화하지 않는다

GitHub Pages의 브라우저 로컬저장값은 GitHub Actions가 읽을 수 없다. 보안과 단순성을 위해 텔레그램은 비중+수익률을 기본으로 하고, 금액이 필요할 때만 별도의 비공개 예산 설정을 사용한다.

### 3. 반감기는 반드시 포함하되 단독 명령이 아니다

반감기는 프로토콜상 블록 보조금을 바꾸는 확정적 사건이다. 그러나 가격효과의 크기와 시점은 수요·유동성·레버리지·거시환경에 따라 달라질 수 있다. 따라서 반감기 진행률은 모든 상태판정에 포함하지만 가격·추세·온체인 증거 없이 전액매수·전액매도하지 않는다.

### 4. 상태 머신을 운영 기본으로 한다

```text
WAIT → WATCH → ACCUMULATE_1 → ACCUMULATE_2
→ CONFIRM_BUY → TREND_HOLD → FULL_HOLD
→ REDUCE_1 → REDUCE_2 → CORE_ONLY → EXIT
```

이 구조는 어떤 증거로 비중이 변했는지 설명할 수 있고, 알림 중복·쿨다운·데이터 오류를 명확히 처리할 수 있다.

### 5. 과거 최고 성과 하나를 최종 전략으로 채택하지 않는다

반감기 이벤트 수가 적고 기술규칙은 데이터 스누핑에 취약하다. 따라서 워크포워드, cycle holdout, 비용·슬리피지, 임계값 주변 민감도, 데이터 지연을 통과한 후보만 남긴다.
