# BTC·ISA 알림 신뢰성 최종 재검토 — 2026-09-05

## 범위

실제 주문은 계속 사용자가 직접 실행한다. BTC 62.5/65% 및 다음 epoch 35/36/37/38%, 초기예산 1,000만원, ISA 기존 3종목·초기 추가 1,000만원·월 50만원은 변경하지 않는다. 전략 수익률 최적화 작업이 아니다.

## 계획에서 바꾼 결정

1. 15분 slot 전체를 건너뛰는 중복 방지는 사용하지 않는다. 같은 시간대에 도착한 잔고 입력·체결확인이 막힐 수 있다. 운영 workflow를 직렬 실행하고, BTC 주간 판단과 pending, ISA 월간 발송 키로 중복 주문안을 제한한다. PR 테스트는 운영 concurrency와 분리한다.
2. GitHub cache와 Cloudflare KV 중 revision이 큰 것을 자동 채택하지 않는다. 계좌 상태의 주 저장소를 이번 작업에서 이전하지 않는다. 외부 Durable Object에는 감시 기록만 저장한다.
3. 월요일에 충족되지 않았을 수도 있는 조건을 화요일에 소급 충족시킨 것으로 보지 않는다. 늦게 관측된 임계값은 보수적으로 처리한다.

## BTC 지연 점검

`last_official_monday`는 실제 실행일이 아닌 해당 주 월요일 날짜를 보존한다. 현재 주만 보충하며 여러 주의 주문을 재생하지 않는다. 한 번에 한 단계, pending sync 차단은 유지한다.

월요일에는 기존 판정을 유지한다. 화~일에는 동일 epoch/매수·매도 단계의 조건 충족을 월요일 09:17 이전에 관측한 이력이 있어야 주문안을 만든다. 이력은 `strategy.official_eligibility`에 추가 저장된다. 이력이 없거나 임계값을 화요일에 처음 관측했다면 `BTC 지연 점검 · 주문 보류` 안내 후 다음 공식 월요일까지 기다린다. 따라서 모든 누락을 무조건 보충하는 방식은 아니다. 거래시점 앞당김을 방지하기 위한 보수적 제한이다.

`last_official_execution`과 pending에 예정시각·실제시각·정시/지연/보류 모드를 기록한다. 주문금액은 현재 조회 가격과 마지막 수동동기화 잔고를 사용하며 과거 가격으로 소급하지 않는다.

3영업일 준비 알림을 먼저 전달했다면 빠뜨린 5영업일 알림은 뒤늦게 보내지 않는다. 예상일은 10분/블록, 월~금 기준 근사이며 한국 공휴일 미반영이라는 기존 한계를 유지한다.

## ISA 실제 누락 원인 수정

내부 월간 판정은 늦게 처리할 수 있었지만, 외부 호출이 09:10~09:30에 제한돼 있었다. 이제 평일 09:17 이후 첫 실행에서 확인하며, 당월 미발송 또는 데이터 오류는 같은 날 1시간 간격으로 재확인한다. 정상 평상시는 하루 한 번이다. 수동 상태조회는 별도 처리하므로 slot 중복 차단으로 막지 않는다.

월간 발송은 초기매수 완료 이후·해당 월 1회다. 누락된 전월들의 50만원을 합산하지 않는다. 당월 시세이면서 미래 날짜가 아니고 7일 이내인 참고시세만 월간 주문안에 사용한다. 첫 거래일 아침에 당월 종가가 아직 없으면 확인 가능한 다음 실행으로 늦어질 수 있다. 실시간 지정가 주문은 사용자가 확인한다.

초기매수 안내와 주간 재안내는 `1,000만원 - 동기화된 누적 TIGER 매수원금`만 계산한다. 이미 매수했으나 동기화하지 않은 경우에는 다시 주문하지 말고 먼저 동기화하도록 안내한다. 알림 발송과 실제 체결 완료를 혼동하지 않는다.

## 실행 공백·상태 메시지

평상시는 3시간, 주문·동기화·임계구간 임박 상태는 90분부터 복구 시 경고한다. 12시간 반복 제한과 심각도 상승 예외가 있다. 정상 외부 복구 호출도 최근 실행시각에 포함해 cron만 늦었다고 경고하지 않는다. 아직 외부 감시가 없으면 중단 중의 실시간 장애 알림은 불가능하다.

`GitHub Actions가 멈췄다`고 단정하지 않고 `이 워크플로의 실행 공백`으로 표시한다. 메시지 작성 시점에 아직 완료되지 않은 원격 cache 저장이나 미래 예약 실행을 정상이라고 단정하지 않는다. ISA를 이번 실행에서 조회하지 않았다면 마지막 저장 상태라는 사실을 표시한다.

## 상태 보호·운영 건강상태

기존 BTC/ISA cache prefix는 유지한다. 운영 실행 전에 두 상태파일이 존재하고 같은 run/attempt에서 복원됐는지 검사한다. cache 미스·서로 다른 복원 revision·NaN·알 수 없는 버전이면 새 1,000만원 계좌로 초기화하지 않고 중단한다. 정상 수동 입력은 허용하며 계좌 생성시각과 Telegram offset 역행만 추가 검사한다.

명시적인 사람의 일반 수동 실행만 기존 reset 옵션을 사용할 수 있다. `service_only=true` 또는 외부 watchdog은 초기화를 요청할 수 없다. 정상 거래를 위해 reset을 사용하지 않는다.

유효한 로컬 상태는 서비스 후속 실패에도 가능한 한 기존 cache에 저장한다. 두 cache를 동시에 원자적으로 저장하는 것은 아니므로 한쪽 저장만 실패하면 다음 실행을 차단하고 수동으로 같은 완료 revision을 복원해야 한다. 강한 내구성 저장소 이전이나 end-to-end exactly-once 전송을 완료했다고 주장하지 않는다. Telegram 전송 뒤 프로세스 강제 종료 같은 경우 중복 메시지 가능성은 남는다.

`publish-health`는 service 종료 후 별도 job에서 `needs.service.result`로 게시한다. 데이터 오류를 단순 green 성공으로 가리지 않는다. 사용자 계좌 잔고는 증권사·업비트 API로 자동 대조한 값이 아니라 수동 입력값이다.

## 외부 감시 — 소스 준비, 배포는 별도

`infra/watchdog`는 Cloudflare Cron + SQLite Durable Object 기반이다. 기본 `ENABLED=false`, `ENABLE_RECOVERY=false`이며 연결·비밀값 설정 전에는 실행되지 않는다. 이 작업 환경에는 Cloudflare 배포 연결이 없어 외부 감시 활성화를 완료할 수 없다.

30분 넘게 검증된 main 운영 성공이 없으면 안전한 경량 workflow_dispatch를 요청하고, 90분 넘으면 Telegram 직접 경고한다. 현재 실행/대기 작업, 재호출 냉각시간, 전송 실패를 점검한다. PR/다른 workflow/옛 건강상태 없는 실행은 성공으로 세지 않는다. 새 건강상태 계약의 첫 정상 운영 실행이 확인되지 않으면 자동 호출하지 않는다. dispatch HTTP 접수는 복구 성공이 아니다.

세부 비밀값 설치·활성화·검증·중단 절차는 `infra/watchdog/README.md`를 따른다. 상태 초기화·자동주문·Telegram getUpdates는 외부 감시에서 사용하지 않는다.

## 검증

기존 회귀 테스트, 현재 주만 보충, 임계값 후발 관측 보류, pending 보존, 같은 주/월 중복 방지, ISA 오후 호출, 부분매수 잔여액, 복구 경고, cache 미스/불일치/비정상 값, 경량 runtime 외부 패키지 없이 import, 외부 watchdog의 가짜 HTTP 테스트를 실행한다. 실제 배포 성공 여부와 외부 배포 여부는 PR·운영 run 결과로 별도 보고한다.
